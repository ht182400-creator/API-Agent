## 问题一：Python 缓存导致服务加载旧代码

### 现象
服务日志显示 `NameError: name 'logger' is not defined`，但代码中 logger 已定义。

### 根本原因
Python 的 `__pycache__` 缓存了旧版本的模块，导致服务加载的是未定义 logger 的旧代码。

### 解决步骤
1. 停止所有 Python 进程
2. 清除所有 `__pycache__` 目录
3. 重新启动服务（使用 `--reload` 参数）

### 预防措施
- 修改代码后，如果服务没有自动重载，需手动重启
- 定期清理 `__pycache__` 缓存

## 问题二：支付宝回调签名验证失败

### 现象
- 支付宝扫码付款成功
- 支付宝回调返回 `{"success": false, "message": ""}`
- 商户页面停留在二维码扫描阶段

### 根本原因
`verify_with_rsa()` 函数期望 message 参数是**有 `read()` 方法的对象**（BytesIO），而不是字符串。

**错误位置**: `src/api/v1/payment.py` 约第 654 行

**错误代码**:
```python
sign_content = "&".join(sign_parts)
is_valid = verify_with_rsa(settings.get_alipay_public_key(), sign_content, signature)
```

**修复代码**:
```python
sign_content = "&".join(sign_parts)

# 验证签名：verify_with_rsa 需要 message 是有 read() 方法的对象
from io import BytesIO
message_stream = BytesIO(sign_content.encode('utf-8'))
is_valid = verify_with_rsa(settings.get_alipay_public_key(), message_stream, signature)
```

### 相关文件
- `src/api/v1/payment.py` - 支付宝回调处理函数
- `logs/errors_20260508.log` - 错误日志

## 问题六：二维码倒计时显示为0秒（时区混淆bug）

### 现象
- 点击"立即充值"后，页面显示"二维码有效期：0秒"
- 用户还未来得及扫码支付，二维码就已过期

### 根本原因
**时区混淆bug**：`calculate_expires_in` 函数假设 naive datetime 是本地时间（UTC+8），但数据库实际存储的是 UTC 时间，导致时间计算错误。

### 修复方案
`calculate_expires_in` 函数将 naive datetime 假定为 **UTC 时间**（与数据库实际存储一致），并添加防御性检查和日志：

```python
def calculate_expires_in(created_at: datetime) -> int:
    if created_at is None:
        return 600  # 默认值
    
    now_utc = utc_now()
    
    if created_at.tzinfo is None:
        # 假定为 UTC 时间
        utc_tz = timezone.utc
        created_at_aware = created_at.replace(tzinfo=utc_tz)
    else:
        created_at_aware = created_at
    
    expiry_time = created_at_aware + timedelta(minutes=ORDER_EXPIRY_MINUTES)
    remaining = (expiry_time - now_utc).total_seconds()
    
    # 异常检查
    if remaining > ORDER_EXPIRY_MINUTES * 60 * 2 or remaining < 0:
        return 600
    
    return max(0, int(remaining))
```

## 问题七：前端时间显示为 UTC 时间而非本地时间

### 现象
- 充值记录、API Key 创建时间等显示为 UTC 时间（比本地时间晚 8 小时）
- 例如：当前时间 11:06，记录显示 03:04

### 根本原因
数据库存储的是 UTC 时间，但前端使用 `dayjs(date).format()` 解析 ISO 字符串时没有正确转换为本地时区。

### 修复方案
创建统一的日期格式化工具 `formatLocalDateTime`：

```typescript
// web/src/utils/dateFormat.ts
export function formatLocalDateTime(utcString: string, format: string = 'YYYY-MM-DD HH:mm:ss'): string {
  const date = new Date(utcString)
  if (isNaN(date.getTime())) return '-'
  
  // 提取本地时间并格式化
  const year = date.getFullYear()
  const month = String(date.getMonth() + 1).padStart(2, '0')
  const day = String(date.getDate()).padStart(2, '0')
  const hours = String(date.getHours()).padStart(2, '0')
  const minutes = String(date.getMinutes()).padStart(2, '0')
  const seconds = String(date.getSeconds()).padStart(2, '0')
  
  return format.replace('YYYY', year).replace('MM', month)...
}
```

## 问题五：React 状态异步导致轮询循环立即退出

### 现象
- `[DEBUG] startQrcodePolling 函数被调用` 日志正常输出
- **没有** `[QRCode Poll] 第 1 次` 日志
- 轮询循环根本没有执行

### 根本原因
React 状态更新是**异步**的！

```typescript
const startQrcodePolling = async (paymentNo: string) => {
  setQrcodePolling(true)  // 异步！不会立即生效
  const intervals = [...]
  
  for (let i = 0; i < intervals.length; i++) {
    if (!qrcodePolling) break  // ❌ 检查时还是 false，立即退出循环
    // ...
  }
}
```

### 修复方案
使用**局部变量**替代 React 状态来控制循环：

```typescript
const startQrcodePolling = async (paymentNo: string) => {
  setQrcodePolling(true)
  let isPolling = true  // ✅ 局部变量，立即生效
  const intervals = [2000, 2000, 2000, 3000, 3000, 5000, 5000, 10000]
  
  for (let i = 0; i < intervals.length; i++) {
    if (!isPolling) break  // ✅ 现在检查的是局部变量
    // ...
    if (status.status === 'completed') {
      isPolling = false
      setQrcodePolling(false)  // 循环结束后再更新状态
      handleQrcodePaymentSuccess(status)
      return
    }
    // ...
  }
}
```

### 跳转支付是否有同样问题？
**没有**。跳转支付 `handleAlipayCallback` 内部定义了 `pollPaymentStatus` 函数，使用的是局部变量 `intervals`，不受 React 状态异步影响。

### 相关文件
- `web/src/pages/developer/Recharge.tsx`

### 经验总结
1. **React 状态更新是批处理异步的**：调用 `setState` 后立即读取，值可能还没更新
2. **轮询循环不要依赖外部状态作为退出条件**：使用局部变量
3. **正确模式**：`setState(true)` + `let isRunning = true` + `if (!isRunning) break`

---

### 时区处理经验总结
1. **统一使用 UTC 存储**：数据库中的时间字段应统一存储为 UTC 时间
2. **数据库连接层强制时区**：在 `create_engine` 中使用 `connect_args={"options": "-c timezone=utc"}` 强制数据库使用 UTC
3. **不要依赖假设**：不要假设 naive datetime 是 UTC 还是本地时间，应该在数据库连接层面统一
4. **前端显示时转换**：在需要显示给用户时，再将 UTC 时间转换为本地时区
5. **添加调试日志**：时区问题很难排查，应该在关键位置添加日志

## 问题四：JavaScript 函数定义顺序问题（变量提升）

### 现象
- 前端代码已添加 `startQrcodePolling()` 调用
- 控制台没有 `[DEBUG]` 日志输出
- 后端日志显示只有手动刷新，没有自动轮询

### 根本原因
**JavaScript/TypeScript 中，`const` 和 `let` 声明的函数表达式不会提升（hoisting）**。

函数定义顺序：
```
handleCreateOrder (443行) → 调用 startQrcodePolling → 运行时 startQrcodePolling = undefined ❌
startQrcodePolling (549行) → 函数定义位置
```

由于 `startQrcodePolling` 在 `handleCreateOrder` **之后**定义，调用时它是 `undefined`，导致静默失败（不会报错）。

### 修复方案
将 `startQrcodePolling` 和 `handleQrcodePaymentSuccess` 函数移到 `handleCreateOrder` **之前**定义。

**正确顺序**：
```typescript
// 第 388 行：先定义轮询函数
const startQrcodePolling = async (paymentNo: string) => { ... }

// 第 420 行
const handleQrcodePaymentSuccess = async (status: any) => { ... }

// 第 443 行：再定义使用轮询的函数
const handleCreateOrder = async () => {
    // ...
    startQrcodePolling(payment.payment_no) // 现在可以正常调用 ✅
}
```

### 相关文件
- `web/src/pages/developer/Recharge.tsx`

### 经验总结
1. **ES6 `const/let` 不 hoist**：使用 `const` 声明的箭头函数不会被提升
2. **函数声明 `function` 会 hoist**：传统 `function fn() {}` 可以放在调用之后
3. **最佳实践**：将辅助函数（特别是被其他函数调用的）放在文件顶部或使用前定义
